# Phase 6 — Security and Permission Analysis

All findings in this document are **static observations of the shipped APK's contents** (manifest declarations, embedded string literals, resource XML). Nothing here was produced by running the app, intercepting its traffic, or interacting with any live backend. Severity language ("notable", "worth reviewing") reflects general Android security hygiene norms, not a confirmed exploit — none was attempted or verified, per the task's constraints.

## 6.1 Runtime permissions requested
| Permission | Purpose (typical) |
|---|---|
| `CAMERA` | QR scanning, NID/selfie capture (eKYC), receipt photos |
| `READ_CONTACTS` | Likely contact-picker for quick customer entry |
| `ACCESS_FINE_LOCATION`, `ACCESS_COARSE_LOCATION` | Ties to the `locations` Room table (Phase 3) |
| `READ_PHONE_STATE` | Device/SIM identification (common for OTP flows, fraud signals) |
| `READ_EXTERNAL_STORAGE` / `WRITE_EXTERNAL_STORAGE` (maxSdk 28 on write) | Document/receipt-photo upload; write permission correctly scoped out on API 29+ (scoped storage) |
| `USE_FINGERPRINT` | Biometric unlock for the app's PIN lock (older API; modern apps also use `USE_BIOMETRIC`, not seen) |
| `POST_NOTIFICATIONS`, `FOREGROUND_SERVICE` | Push notifications, `ShakeService` running in foreground |
| `ACCESS_NETWORK_STATE`, `ACCESS_WIFI_STATE`, `INTERNET`, `WAKE_LOCK` | Standard networking/background-sync support |
| `VIBRATE` | UI feedback |
| `com.google.android.c2dm.permission.RECEIVE` | FCM push transport |
| `com.google.android.gms.permission.AD_ID` | Google Advertising ID access (ties to `GAIDSyncWorker`, Phase 2) |
| `com.google.android.finsky.permission.BIND_GET_INSTALL_REFERRER_SERVICE` | Play install-referrer (attribution) |
| `com.progoti.tallykhata.DYNAMIC_RECEIVER_NOT_EXPORTED_PERMISSION` | Self-declared `signature`-level permission (`protectionLevel=0x2`) auto-generated by AndroidX for dynamically-registered non-exported broadcast receivers (standard boilerplate, not a custom security control) |

**Notably absent:** `READ_SMS` / `RECEIVE_SMS`. OTP auto-fill is implemented via the privacy-friendly **Google SMS Retriever API** instead — confirmed by `TKSMSReceiver`'s single intent-filter action `com.google.android.gms.auth.api.phone.SMS_RETRIEVED`, which requires no SMS permission and only delivers messages matching an app-specific hash. This is a positive finding (least-privilege OTP handling). No `READ_CALL_LOG`, `RECORD_AUDIO`, `BODY_SENSORS`, or `READ_SMS`/broad-SMS permissions are requested at all.

## 6.2 Exported component review
### ContentProviders — all `exported="false"`
All 8 providers (`FileProvider`, `ImagePickerFileProvider`, MLKit/Firebase/AdMob/Facebook/startup/Picasso init-providers) are explicitly non-exported. The two app-relevant file providers (`FileProvider`, `ImagePickerFileProvider`) additionally use `grantUriPermissions="true"`, the correct, scoped pattern for sharing specific files (e.g. a receipt photo) with another app via a one-time URI grant rather than broad exposure.

### Services/Receivers — app-owned ones are not exported
`PushNotificationMessageService` and `ShakeService` (the only 2 app-owned services) are both non-exported. `TKSMSReceiver` (the only app-owned receiver) is `exported="true"`, but is gated by its OS-enforced intent-filter action (`SMS_RETRIEVED`, broadcast only by Google Play Services with a matching app hash) — standard and expected for this API.

### ⚠️ Activities — 24 explicitly `exported="true"` with no `<intent-filter>`
Besides the two activities that legitimately need `exported="true"` for their declared intent-filters (`SplashScreenActivity` — `MAIN`/`LAUNCHER`; `MainActivity` — an `https://www.tallykhata.com/openActivity` App Link with `autoVerify="true"`), **24 further app activities carry `android:exported="true"` explicitly set in the manifest despite having no `<intent-filter>` at all.** Examples include PIN-confirmation/destructive-action screens and report builders:
```
ConfirmCashBoxEditDeleteWithPIN, CashBoxTxnEditActivity, PromptAccountChooserActivity,
ShowUnverifiedNumberActivity, PostVerificationDeviceChooserActivity,
CashBoxDetailPdfActivity, CashReportSummeryPdfActivity, MonthlyBakiPdfBuilderActivity,
DailyBakiPdfBuilderActivity, ... (full list in evidence/01_manifest_parsed.json)
```
**Why this is worth flagging:** an Activity without an intent-filter does not *need* `exported="true"` for any normal OS-level use case (it's only reachable by another app that already knows its exact component name and constructs an explicit `Intent`) — so this is very likely either (a) intentional, to let a specific first-party companion app/tool launch these screens directly, or (b) incidental over-permissioning (e.g. a shared base-manifest fragment or lint-suppression applied too broadly). Because several of these are **PIN-gated destructive-action or financial-report screens**, if any of them fail to independently re-verify the PIN/session when launched (i.e., if they trust that only internal navigation reaches them), a malicious app with no permissions beyond "be installed" could attempt to launch them directly with a crafted Intent and skip the normal navigation path. **This project did not and could not test whether such an attack succeeds** — that would require either dynamic testing (installing a second, attacking app and attempting to launch these components, which is runtime/dynamic analysis not performed here) or full bytecode decompilation of each activity's `onCreate`to check for independent auth checks (also not performed — see `09_technical_limitations.md`). This is reported as a configuration observation for the app owner to review, not a confirmed vulnerability.

### Third-party-library exported components (lower relevance, listed for completeness)
`com.google.android.gms.auth.api.signin.RevocationBoundService` (exported, but permission-gated to `com.google.android.gms.auth.api.signin.permission.REVOCATION_NOTIFICATION`), `androidx.work.impl.background.systemjob.SystemJobService` (exported, `BIND_JOB_SERVICE`-gated — standard OS pattern), `com.google.android.play.core.assetpacks.AssetPackExtractionService` (exported, standard Play Asset Delivery component), `FirebaseInstanceIdReceiver`/`AppMeasurementReceiver`/WorkManager's diagnostics & profile-installer receivers (all standard AndroidX/Firebase boilerplate, each permission- or signature-gated appropriately by the OS). None of these are unusual for a modern Android app.

## 6.3 Network transport security
- `android:usesCleartextTraffic="false"` at the application level (manifest default-deny for plaintext HTTP) — good baseline.
- **⚠️ Exception carved out in `res/xml/network_security_config.xml`:**
  ```xml
  <network-security-config>
    <domain-config cleartextTrafficPermitted="true">
      <domain includeSubdomains="true">182.163.100.230</domain>
    </domain-config>
  </network-security-config>
  ```
  This explicitly **permits unencrypted HTTP traffic to the hardcoded IP address `182.163.100.230`** (a public, non-RFC1918 address — this analysis did not contact it, resolve its ownership, or make any assumption about what service runs there). Any data sent to this address — if the app actually does send anything there, which was not verified — would be visible to anyone on the network path (no TLS, no integrity/confidentiality). This is a concrete, worth-reviewing finding: either this is a legitimate, deliberate exception (e.g., a local/LAN device, a legacy integration) that should ideally be migrated to TLS, or it's a leftover from development/testing that should be removed from the production config.
- A **staging/test gateway URL was found hardcoded in production app code**: `http://gw.staging.nobopay.com/api/v1/` — both non-production (`staging`) and unencrypted (`http://`). Shipping a staging endpoint in a production build is a process hygiene issue (even if unreachable/decommissioned, it signals the staging/prod URL selection may be a compile-time constant rather than a build-flavor-specific config, raising the risk of accidentally routing production traffic to a test environment, or vice versa).
- No app-specific OkHttp `CertificatePinner` pin hashes (`sha256/...` literals) were found — only the OkHttp library's own internal format-string template. The *capability* to pin certificates exists in the dependency (OkHttp ships `CertificatePinner`), but no evidence of the app actually configuring a pin was found. Absence of evidence is not evidence of absence here — pins could in principle be constructed dynamically rather than as a literal, though that is an unusual pattern — but at minimum, no static certificate pinning was confirmed.

## 6.4 Hardcoded credential-like value in the manifest
```xml
<meta-data android:name="surecash-client-key" android:value="abcd457865938sdjhf" />
<meta-data android:name="surecash-client-name" android:value="Uthao" />
<meta-data android:name="surecash-client-id" android:value="uthao" />
```
`surecash-client-key` is a **literal, hardcoded string value directly in `AndroidManifest.xml`** (unlike the other SureCash config value, `com.surecash.sdk.api_base_url`, which is a proper `@resource` reference). Any manifest value is trivially extractable from the public APK by anyone (as demonstrated by this analysis itself, with zero special tooling). Whether this string functions as a real shared secret (in which case embedding it client-side is a design weakness inherent to any client-embedded secret — it cannot be kept confidential in a distributed APK) or merely as a non-sensitive SDK/client identifier (akin to an API "client ID" rather than a "client secret") could not be determined without SureCash SDK documentation or decompiled logic showing how it's used. It is flagged here simply because it is now a matter of public record once the APK is downloadable (as it already is, being on Google Play).

## 6.5 Bundled debug-bridge library
`com.facebook.stetho.*` (519 classes, Facebook's Chrome-DevTools debugging bridge for Android — normally used to inspect an app's local SQLite databases, shared preferences, and network traffic from a desktop Chrome browser over `adb`) is present in the compiled DEX. **Whether Stetho is actually initialized at runtime (`Stetho.initializeWithDefaults(this)` or similar, typically gated behind a `BuildConfig.DEBUG` check) could not be confirmed** — that requires decompiling `TallykhataApplication`'s method bodies, which this project's tooling does not support (see `09_technical_limitations.md`). Recommendation for the app owner: confirm Stetho initialization is compiled out of (or conditionally disabled in) release builds, since if it is active, it would allow local, physically-connected debugging access to the app's Room database and network traffic.

## 6.6 Signing / build integrity
See `01_apk_analysis_report.md §1.3`: the APK is signed with Google's Play App Signing re-signing certificate (standard for Play-distributed apps using App Bundles) rather than a developer key being visible in this artifact — this is expected, not a weakness, for a Play Store download. `debuggable` is absent from the manifest (defaults to `false`) — confirmed not a debug build.

## 6.7 Positive security observations (for balance)
- No SMS-reading permission; uses the privacy-scoped SMS Retriever API.
- `allowBackup="false"` — app data is excluded from Android's automatic cloud/ADB backup, appropriate for a financial-ledger app.
- Scoped storage respected (`WRITE_EXTERNAL_STORAGE` capped at `maxSdkVersion=28`).
- File sharing uses `FileProvider`/scoped `grantUriPermissions`, not a broadly exported content provider.
- `androidx.security` (Jetpack Security crypto, `EncryptedSharedPreferences`/`EncryptedFile`) is present in the dependency graph, suggesting at least some local data is encrypted at rest (which specific data was not confirmed without decompilation).
- Application-level `usesCleartextTraffic="false"` default, with only one narrow, explicit exception (§6.3).
- Destructive ledger operations (edit/delete of transactions/customers) are uniformly gated behind a PIN-confirmation screen in the declared navigation pattern (Phase 5 §7.2).
